#### Q&A 
 > 原文：在客户端渲染中, 为什么需要在组件首次渲染完成之后, 再去发送请求, 而不是直接发请求, 请求成功之后, 再渲染页面？实际上, 最主要的原因是因为, 我们在客户端渲染的组件, 除了要考虑初始化的逻辑之外, 还需要额外考虑更新的逻辑. 如果要考虑更新逻辑, 我们就不得不借助 useEffect 来执行一部分逻辑
##### question：客户端为什么要考虑更新逻辑？ 
因为React组件是能根据数据动态渲染UI,不是一次性的模板，所以要考虑更新逻辑。

今日任务：
- [ ] 画出 CSR 与 SSR 的请求、取数、拼接、返回流程。
    csr: 用户输入url -> 像服务器发起请求 -> 拿到html字符串模板-> 再向服务器发起请求拿到数据资源 ->浏览器自己拼接数据和模板信息生成页面 -> 浏览器进行渲染
    ssr: 用户输入url -> 像服务器发起请求 -> 服务器根据路由自己去其他服务器拿去数据和模板 -> 服务器自己拼接信息生成页面 -> 浏览器直接拿到页面字符串，直接渲染。
- [ ] 说清服务端生成 HTML、客户端水合，以及优雅降级与全量水合成本。
    服务端生成HTML: 使用ReactDOMServer.renderToString和ReactDOMServer.renderToStaticMarkup生成html string.
    客户端水合： 指的是同构组件在客户端进行执行拿到交互逻辑，也叫注水。
    优雅降级：当服务器出现压力过大，执行过程出现问题时，将服务器渲染调整至客户端渲染，实现兜底的目标。
    全量水合成本：就是浏览器为了接管整颗ssr react 页面所付出的js 下载，执行，组件树重建，dom 匹配和事件恢复成本。🐕
- [ ] 对比同构组件与 RSC，明确服务端依赖为何不应进入客户端包。
    同构组件是在服务器渲染一次，在客户端也渲染一次，所以在客户端，服务器所依赖的包也会下载，整体打包的体积就会变大。
    rsc方案里，只在服务端运行的组件不会在客户端里执行，所以服务端运行组件的依赖只会打包一次。体积量大大减少。
#### 一张“CSR → SSR → 同构 → RSC”的演进图，每一步只写“解决了什么、又带来什么问题”。

**csr:** 解决了开发的效率，能最大程度的快速的构建一个可交互页面。但是所有的资源和代码都在客户端上面，如果有繁重的计算则会加大了客户端的运行压力。首屏依赖 JS 下载、执行和客户端取数，可能导致首屏慢、SEO困难、客户端压力大。
**ssr:** 主要解决首屏内容和 SEO，并且对于复杂的逻辑的页面可以在服务器生成页面，客户端直接渲染，加快页面渲染速度。但只有服务端 HTML、没有客户端 JS 时，React 交互能力有限；请求越多 → 服务端计算压力越大 → 请求开始排队 → TTFB（从浏览器发出请求，到收到服务器返回的第一个字节，等待了多久） 变长。
**同构:** 解决了ssr交互弱的问题，在服务端生成静态页面，客户端重新构建组件树，并与现有 HTML 水合。但是这样比如服务端所依赖的包，在客户端上也要重新加载一边，增大了打包的体积。
**rsc:** 区分了只在服务端运行的组件和同构组件。这样减小的打包的体积，还让纯展示组件不参与客户端水合。目前所在的问题在于服务端/客户端边界、数据序列化和组件拆分复杂度
- [ ] 理解虚拟 DOM、Fiber、真实 DOM 的角色，以及节点复用条件。
    虚拟DOM： 就是jsx 语法编译后的产物-> reactElement 对象。
    Fiber: 基于虚拟DOM对象构建的Fiber对象，里面添加了一些动态的属性，比如fiber 指针，effect tag ，还有一些状态属性等。
    真实DOM：由浏览器api: document.createElement创建的DOM对象，通常在commit阶段，整体插入到DOM中。
    节点复用条件： state、context、props 发生变化，组件重新渲染。最佳实践只考虑state、context的变化。
最小实践：做一个计数器与静态信息区，观察更新范围；通过组件组合让静态区不随计数更新。先自己尝试，卡住后再对照文章。
##### 为什么客户端组件仍可能在服务端执行？为什么浏览器 API 不能直接放在组件函数的初始化路径里？
客户端组件并不等于只在客户端执行。首次加载时，它仍可能在服务端预渲染成 HTML；浏览器加载 JavaScript 后，再恢复 React 组件树并对现有 HTML 进行水合。因此组件初始化和渲染阶段必须兼容服务端环境。浏览器 API 不仅可能因服务端不存在而报错，还可能造成服务端与客户端首次渲染结果不同，导致水合不一致。此类逻辑通常应放在水合后的副作用或用户事件中。
